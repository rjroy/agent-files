# Crucible feasibility against OpenCode V2 plugin host

## Key Findings

- **A native V2 server plugin with tools is supported; the intent's complete lifecycle is not a built-in capability.** V2 plugin registration supports custom tools and tool schemas, and executor context includes an `AbortSignal`. That signal is associated with the invocation/session cancellation, not a durable Crucible run ID; the host docs do not specify that a request which returns promptly can detach a durable job or how one invocation's signal governs later work.
- **Plugin reload/restart cannot be treated as background-job durability.** Plugin `setup` may return cleanup; unload disposes registrations. Global/project plugin/config changes are watched, while some local dependency changes require restart. The V2 location-reload API rebuilds services but says running sessions continue with fresh services at the next step boundary. No V2 source promises that arbitrary plugin-owned async tasks survive reload, restart, or process exit. Persist run state and treat execution recovery as a separate unresolved policy; the intent's “no automatic crash resumption” is compatible with marking interrupted runs incomplete.
- **The proposed `crucible.json` files are not OpenCode's native configuration files.** V2 native config loads `opencode.json`/`.jsonc`; plugin `ctx.options` comes from a plugin entry in that config. OpenCode does not document automatic loading/merge of a plugin-specific `crucible.json` at global and project paths. This is feasible only as Crucible-owned file loading/validation, explicitly scoped to the canonical project and global OpenCode config directory, with precedence and reload semantics implemented and tested by Crucible.
- **Model-facing tools can plausibly start plugin-owned background work; this is not a host-provided durable job primitive.** V2 plugin docs demonstrate detached background activity during setup (event subscription via `void (async () => ...)()`) and an interval with cleanup. This establishes a supported pattern for plugin-owned activity, but not that work survives tool return, plugin reload, or process restart. Tool and RPC handlers both receive cancellation signals. A Crucible runner can be owned by the plugin and surfaced through tools; RPC is optional if typed client methods/events are useful, not a necessary or more durable job mechanism. Persist run state and test lifecycle behavior.
- **OpenCode can distribute a companion skill independently**, with global and project discovery and later-source precedence; alternatively a plugin can register a skill through `ctx.skill.transform`. A global + project skill duplicate can override by ID. This is not the config mechanism for reviewer/arbiter models and should not be treated as substitute plugin behavior.
- **omo-slim remains a configuration concern, not an execution dependency.** Crucible's approved intent explicitly keeps workforce orchestration with omo-slim and review stages inside Crucible. Existing local `config/oh-my-opencode-slim.json` is package-specific configuration; V2 docs do not define how it loads plugins. Register Crucible via OpenCode V2's plugin config/discovery rather than assuming omo-slim discovers or drives it. No local setup was changed or behaviorally tested.

## Follow-up: practical host mapping (retrieved 2026-10-26)

This follow-up narrows uncertainty to the smallest supported shape, without treating undocumented host guarantees as impossible:

- **Use a V2 server plugin to own the lifecycle runner; expose lifecycle operations as model-facing tools.** V2 Build Plugins explicitly demonstrates plugin-owned background activity in `setup` (an unawaited async event-consumer loop) and an interval, with cleanup functions aborting/clearing those resources. This makes a background runner a reasonable implementation pattern, not a promise that tool-started work survives tool return, plugin reload, or process restart. Have begin validate/persist a run and return its ID, then schedule plugin-owned work with a run-level `AbortController`; persist stage transitions and have status/read derive from disk. Explicit abort should update persisted state and abort in-memory controllers for that run. On cleanup, stop scheduling and abort/flush best-effort, leaving active records visibly interrupted. These are implementation choices; lifecycle edge behavior still needs runtime tests.
- **Keep tool invocation cancellation distinct from run cancellation.** V2 says `context.signal` supports cancellation when the owning Session is stopped; it does not specify abort on invocation return, plugin unload, or location reload. The tool context's complete type/location contract is not documented, but the permission example explicitly uses `context.sessionID`, `context.agent`, `context.messageID`, and `context.id`. These provide invocation identity evidence; they do not supply a durable Crucible run ID or prove how signals behave for detached work. Propagate the host signal to awaited work in that call; for detached work, use a separate run-owned controller and define whether/when caller cancellation should cancel the review. Use explicit run-ID fencing rather than assuming call identity alone protects later mutations.
- **Project scope is the largest host-integration ambiguity.** `ctx.location.project.canonical` gives the plugin instance's canonical project path, but the docs explicitly warn that `ctx.location` is not every session's location. Tool registration is by plugin runtime; no location parameter is shown for `ctx.tool.transform/list`, and global plugin instances' relationship to project-specific instances is not fully described. The permission example documents `context.sessionID`, `context.agent`, `context.messageID`, and `context.id`, but the complete tool context and a location field are unspecified. Smallest practical probe: use project-local `.opencode/plugins/` with two projects, nested directories, and worktrees; log `ctx.location` and documented call identity fields. If global plugin discovery is needed, verify how a call identifies its project before resolving config and state; do not use plugin instance location as a proxy.
- **Own cross-call serialization in the plugin, backed by the required project-local record files.** A process-local mutex keyed by canonical project + full commit ID is a minimal first implementation for one server process. To satisfy one-active-run under multiple OpenCode processes, use a filesystem lock/atomic exclusive claim and atomic replacement of issue/run JSON; neither plugin `ctx.storage` nor RPC documents CAS/transaction/locking. This follows the intent's serialization requirement; cross-process behavior remains an implementation choice to validate. Worktree aliases should canonicalize to a stable repository identity, not blindly use the active directory string.
- **Custom `crucible.json`: use direct, narrow Node filesystem reads, not native config schema injection.** The official config docs do not establish arbitrary plugin config fields/options merge behavior; the plugin context docs do not offer arbitrary file reading. That is not a prohibition: a plugin can implement its own file loader. Global config directory can be based on the user's OpenCode config directory (V2 docs show `~/.config/opencode` on Linux), project override should resolve from the canonical project as `<canonical>/.opencode/crucible.json`, and application merge must follow the intent's explicit per-field semantics. Validate unknown/malformed model config and freeze the effective config in the persisted run. Global path discovery in non-default XDG/managed setups must be an explicit plugin option or verified through host runtime; don't guess. Hot reload is unnecessary initially: read/validate at `review_begin`; rerun reads fresh values; active runs use their snapshot. This avoids unclear watcher/setup semantics.
- **Companion skill: prefer normal skill files over dynamic registration for the first version.** Install a global `.config/opencode/skills/crucible/SKILL.md` (or a package-provided skill path via config) for general invocation guidance; allow project `.opencode/skills/crucible/SKILL.md` to override on the same ID only intentionally. V2 precedence makes explicit skill paths later than discovered files. The skill can tell the main agent to call Crucible's registered interface, but skills are instructions, not code hooks. `ctx.skill.transform` is viable if the plugin needs to package a computed skill, but path and matching caller location need validation. Tool handlers must independently enforce participant/stage authorization; hiding tools from model request `event.tools` alone is documented as request shaping, not an authorization boundary.
- **Permission and credential nuance:** V2 tool definitions do not document a per-tool permissions property. Build Plugins shows `ctx.permission.assert` with action/resources and session/agent/tool-call source; V2 permissions say plugins may define additional action names. Use this for host permission prompts if appropriate, while enforcing participant/stage/record authorization inside each handler. The plugin docs also show `ctx.integration.connection.active(integrationID)` and `.resolve(connection)` for credentials, but do not prove OpenRouter is available through that integration ID or establish which account/key would be selected; test that separately. Do not read secrets during feasibility research.

### Smallest useful runtime probes

1. Register a test tool that starts a delayed, abort-aware plugin-owned operation, immediately returns a run ID, then query persisted status: does it finish after invocation resolves? Does stopping the calling session abort its run-owned controller or only awaited tool work? Record exact behavior; docs do not settle either.
2. Keep that operation active while triggering watched config reload, explicit `location.reload`, plugin disable/reload, and full service restart separately. Record cleanup invocation, signal state, whether operation continues, and whether a new plugin instance can read its state. Do not infer restart survival from V2 storage's adjective “durable.”
3. Test project-local plugin registration with two projects and nested directories plus worktrees: enumerate tool availability, record `ctx.location` and executor context fields, invoke the same tool in both locations, and confirm the run goes to the correct canonical project. Repeat with one global plugin registration to establish or reject cross-location visibility.
4. Concurrently call begin twice for the same full commit from two sessions; repeat across two OpenCode processes if supported. Confirm one active run, unique run IDs only on explicit rerun, no clobbered issue writes, and stable behavior through a worktree alias.
5. Load a global skill and same-ID project skill; inspect which text is advertised/loaded and whether the tool remains independently callable. Verify caller stage restrictions by attempting every tool action with a wrong participant and wrong phase, not by checking prompt visibility.

These probes test the high-impact runtime gaps only. They do not test model quality or replicate the separate reviewer-execution research lane.

## Evidence and feasibility by concern

### Plugin loading and lifecycle

Official [V2 Plugins](https://opencode.ai/v2/docs/plugins/) docs (retrieved 2026-10-26) say global plugins are discovered under `~/.config/opencode/plugins/`, project plugins under `.opencode/plugins/`, or can be configured by package/directory in `opencode.json(c)`. Configured paths must be directories with `server` or `index` module; a single-file path is skipped. Plugin arrays merge across config layers. Watched config directories reload automatically, while changes to unwatched local dependencies may require restarting OpenCode.

Official [V2 Build Plugins](https://opencode.ai/v2/docs/build/plugins/) says `setup` runs when loaded and may return a cleanup function at unload. Transform registrations can be disposed, and unloading also disposes them. This proves registration cleanup capability, **not** reliable cancellation/join of arbitrary promises spawned by a plugin. Any plugin-owned worker must arrange its own lifecycle cleanup and persist state before it is interrupted; exact reload ordering and timeout behavior are undocumented.

The V2 [HTTP API](https://opencode.ai/v2/docs/api) labels routes experimental. `POST /api/location/reload` rebuilds every loaded location, cancels pending permissions/forms, and says running sessions continue with fresh services at their next step boundary. This does not promise an arbitrary plugin task survives or resumes. The official documentation says nothing about durable plugin task scheduling across process restart. Intent is already explicit that automatic crash resumption is out of scope: interrupted persisted state should be inspectable as incomplete rather than inferred complete.

### Tools, caller context, abort, and async work

Official [Build Plugins — Tools](https://opencode.ai/v2/docs/build/plugins/#tools) documents registration with `ctx.tool.transform`, JSON-schema input (`type`, `properties`, `required`, `additionalProperties`), async `execute(input, context)`, `context.signal`, and `context.progress(...)`. The permission example on that page explicitly uses `context.sessionID`, `context.agent`, `context.messageID`, and `context.id`. Thus, **cancellation and these invocation identity fields are documented**; the complete executor-context type, project/location field, and signal behavior beyond stopping the Session are not. The signal is not documented as a Crucible run-ID cancellation handle or as guaranteeing durable background execution.

Important lifecycle uncertainty: if a begin tool awaits all seven review stages, it will not return promptly. It can instead start/hand work to a plugin-owned runner and return initial status; setup background-loop and timer examples establish plugin-owned async activity as a supported pattern. The docs still do not establish that tool-started detached work remains alive or how it relates to tool/session signals, plugin reload, or restart. An ordinary tool can also be interrupted with its owning session; do not equate that with explicit `review_abort(commit_id)` semantics.

The V2 [RPC](https://opencode.ai/v2/docs/build/plugins/rpc/) docs provide typed plugin methods and events; method handlers receive a `signal` for cancellation and can return structured results. RPC is an optional typed client surface for controlled state/status operations, not required for the model-facing workflow and not a more durable job mechanism. The docs do not promise RPC handlers outlive their request or offer a job queue. RPC events/subscriptions are explicitly live-only: disconnected consumers miss events. Therefore use persisted state as authority, not a stream as the only record of progress.

### Configuration ownership and scope

Official [V2 Config](https://opencode.ai/v2/docs/config/) defines global `~/.config/opencode/opencode.json(c)` and project `opencode.json(c)` or `.opencode/opencode.json(c)`; configs merge in precedence order. It does not define arbitrary `crucible.json` discovery. The plugin docs' `ctx.options` only exposes options supplied in the plugin registration object, and the docs do not describe a general API to enumerate/read arbitrary config files. Thus, the intent's global `crucible.json` and project `.opencode/crucible.json` are valid *application-owned conventions*, not host-recognized config. Crucible must own path resolution, parsing, validation, merge/replacement semantics (reviewer list replace, missing fields inherit, arbiter object replace), and effective-config snapshot per run. Do not expect project entries to be merged into OpenCode configuration automatically.

The [V2 plugin context](https://opencode.ai/v2/docs/build/plugins/) exposes `ctx.location` fields `directory`, optional `workspaceID`, and project `id`, `directory`, `canonical`; docs warn that this is the plugin instance's location, not every session's location. The permission example also establishes tool context fields `sessionID`, `agent`, `messageID`, and `id`, but not its complete type or a project/location field. Use known call identity for diagnostics and permission checks, while resolving/validating active project explicitly at invocation; key locks/state to canonical project plus full commit ID (design implication), not a process-global commit string.

### State ownership, persistence, multi-project concurrency

Intent specifies `.crucible/reviews/<commit_id>/...` in the consuming project and one active run per commit. The V2 plugin API has `ctx.storage` with JSON `get/set/remove/scan`, documented as durable and plugin-scoped, but its docs do not specify a project-scoped key namespace, transaction/CAS semantics, atomicity, or multi-process locking. Plugin storage therefore cannot be assumed to meet project-local audit-file requirements or serialize writes safely. RPC likewise supplies no transaction semantics. The intent's project record tree should remain authoritative if retained; plugin storage can hold auxiliary indexes only after scope/consistency is clarified.

V2 plugin docs do document `ctx.vcs.get/status/diff`; status/diff are working-copy views. The intent requires pinned Git object reads for arbitrary commit/baseline and controlled file/list/search access, while the fetched plugin API does **not** document a general filesystem API or Git-object/blob reader. The public V2 HTTP API exposes filesystem routes (read/list/find and experimental write) but does not by itself prove they can address a pinned Git object or safely enforce the intent's no-follow-symlink/no-shell rules. This is a separate substantive feasibility gate: implement a narrowly validated Git-object reader or obtain verified host support; do not substitute the mutable working tree or VCS working diff.

Concurrent calls for separate projects may reach the same loaded plugin instance; fetched docs do not specify tool serialization. Separate project-rooted files avoid path collisions, but atomic writes and active-run uniqueness need explicit locking. A process-local lock would not coordinate multiple OpenCode processes; an on-disk exclusive claim or other cross-process mechanism may be needed (inference). Test races, restart during write, and a project being opened via different directory aliases/worktrees against the canonical identity. The approved intent requires atomic saves and serialization; API docs do not supply those guarantees.

### Companion skill and omo-slim boundary

Official [V2 Skills](https://opencode.ai/v2/docs/skills/) documents global `~/.config/opencode/skills` and project `.opencode/skills`, source precedence, and ID-based override; explicit `skills` paths in config append rather than replace. V2 Build Plugins also documents dynamic `ctx.skill.transform` registration and reload. Either route can make a companion skill discoverable. If project-specific skill content should override global content, same-ID precedence is documented; if the skill is shipped with a package, plugin registration is another viable route. This does not deliver the Crucible execution state machine.

The approved intent says omo-slim owns normal workforce and Crucible owns its participant runs and state (`.lore/work/intents/crucible.md:13-15, 158`). The installed local `oh-my-opencode-slim` config was not inspected in this task; prior lore notes warn its delegation routing is strong, but those are not proof of current V2 plugin load behavior. OpenCode V2 has its own plugin array and plugin lifecycle; there is no cited V2 evidence that an omo-slim `agents` entry or skill invokes/hosts Crucible automatically. Keep invocation discoverable (tool/skill) while leaving stage orchestration to Crucible, and validate coexistence under the exact installed versions before claiming it works.

## Verified vs inferred

**Documented/verified from current official V2 docs:** directory/package plugin loading; plugin setup cleanup and registration disposal; detached event-consumer and interval examples with cleanup; custom tool registration and schema shape; tool context signal and example identity fields (`sessionID`, `agent`, `messageID`, `id`); RPC execution signal; progress callback example; plugin JSON storage API; integration connection `active`/`resolve` methods; native OpenCode config files/precedence; skill discovery and precedence; location context fields; live-only RPC events; VCS status/diff and the absence of a documented plugin filesystem/Git-object API on the fetched plugin page; location reload behavior described above.

**Inferences or unknowns requiring planning/runtime tests:** how a plugin reads and watches user-owned `crucible.json` files; global path discovery from server process environment; detached runner survival/cancellation on tool return, plugin unload, location reload, and process shutdown; whether prompt-returning begin leaves a plugin-owned runner reliably scheduled; per-project location identity in tool calls; tool concurrency/transaction isolation; durable cross-process locking; atomic project artifact writes; resolving safe reads of Git objects under V2; whether OpenRouter credentials appear through the integration API; and whether the exact installed omo-slim release loads/coexists with a Crucible package. No compatibility claim is established by the presence of a local plugin or config file.

## Main blockers for plan

1. **Background lifecycle contract:** prove how a call returns promptly, how run work is kept alive, how abort reaches every outstanding request, and what status reports after reload/shutdown. The V2 task/session model does not document a durable detached job primitive.
2. **Project-scoped custom config:** specify how plugin obtains canonical project + global config paths, reads/validates/reloads them, and applies the required merge semantics without leaking project configuration across locations.
3. **Immutable target access:** V2 docs do not give the plugin a Git-object snapshot reader or general filesystem interface that fulfills the intent's hard safety rules. Must prove a safe reader rather than use working-tree status/diff.
4. **Durable mutation and concurrency:** implement/test atomic issue writes, active-run uniqueness and fencing across concurrent calls (and potentially multiple host processes). `ctx.storage` and RPC docs make no transaction/CAS promise and are not a replacement for project-local records.
5. **Exact host compatibility:** test tool/RPC registration, shared stage-specific tool exposure, reload teardown, cancellation and integration with the actual OpenCode V2 + omo-slim versions. Docs are public contracts/examples, not evidence the user's installation meets them.
