# Workflow comparison opportunity and risk register

## Scope, method, and evidence limits

This register completes the inspection-only investigation for `agents-alv.4`.
It compares the current instruction-and-artifact workflow with the material
mechanisms present in `tmp/local-marketplace`. No clone workflow, test suite,
provider smoke check, network request, installation, configuration change, or
live-host action was performed. Consequently, no entry asserts runtime
effectiveness, OpenCode loading, a running model, or a successful port.

Evidence labels follow the pre-results rubric:

| Label | Meaning in this register |
|---|---|
| Documented | A README, skill, manifest, or portability document describes it. |
| Implemented | Directly inspectable executable source or schema defines it. |
| Tested | A checked-in test directly asserts source behavior. It was not run. |
| Observed | A command or host fact was observed in this review session. |
| Unknown | Evidence is absent, conflicting, or needs an authorized host trial. |

Grades are rubric grades: **B** is direct implementation or checked-in test
source, **C** is a documented claim, and **D** is unknown or conflicting. The
grade is deliberately not elevated by the number of references.

## Key Findings

1. **The inspected host has extensibility surfaces, but loading remains
   unobserved.** The configured OpenCode file structurally contains `skills`,
   `plugin`, and `mcp`, with `skills.paths` an array. Its installed plugin API
   declares agent, catalog, command, integration, reference, and skill hook
   domains. This establishes implementation/configuration availability, not
   that any configured plugin, skill, command, or integration loaded in a
   running session.
2. **The router has a source-backed route to conditional delegation and tool
   enforcement, not proof that those paths were active.** Its delegate tool is
   conditional on configuration/environment; it creates child sessions and
   runs a bounded acceptance path. Its chat and tool hooks track resumes and
   can hard-block tool calls for tracked subagents. These are implementation
   facts only.
3. **The marketplace remains a mixed portability proposition.** Forge and
   Factory provide directly inspectable deterministic code; Teamsters dispatch,
   aliases, Test Automation command/resume, and Ponytail hooks still require a
   host adapter. The POC's portability claims are documented assertions, not
   current-host compatibility results.
4. **The installed CLI version is observed as `1.18.30`, not the previously
   reported `1.18.29`.** Version is not an evidence grade, compatibility
   decision, or runtime-load trace.

## State and instruction conflicts requiring an explicit authority rule

1. **Task and dependency state:** AGENTS names Beads and its local Dolt store as
   authoritative, with `issues.jsonl` passive ([AGENTS.md](../../../AGENTS.md),
   lines 36-43). Forge graph and Factory ledger represent parallel task state;
   no cited source bridges them.
2. **Working context and recovery:** `.lore/work/notes` and Test Automation's
   `.claude/.test-loop-state.md` can both claim the active phase. Forge
   verification and Factory reports add further, differently scoped context.
3. **Knowledge:** Field Guide ingestion curates work artifacts into
   `.lore/reference` ([ingest/SKILL.md](../../../plugins/field-guide/skills/ingest/SKILL.md),
   lines 6-33). It is not a run-state store. Do not use it as a competing
   completion authority.
4. **Instruction and policy precedence:** current repository instructions,
   skills, Claude/Codex-specific artifacts, Teamsters Markdown, and Ponytail
   injection can issue incompatible directions. Host discovery/loading is
   unknown, so precedence must be specified before any hybrid trial.

## Decision-relevant conclusion

The credible opportunities are narrow and separable: deterministic Factory
gating, Forge evidence/state validation, and perhaps a deliberately invoked
policy skill. The credible risks are also material: multiple durable state
authorities, Claude-specific dispatch/aliases/hooks, unverified OpenCode
registration, partial-success semantics, and sensitive telemetry/provider
egress. This evidence supports designing bounded alternatives and trials, not
adoption or replacement. Per the rubric, absent supported surfaces and host
traces leave OpenCode feasibility inconclusive.
