# Evidence-backed workflow comparison recommendation

## Key findings

The prior recommendation correctly rejected importing the marketplace as an OpenCode workflow. It incorrectly let that compatibility conclusion suppress a separate question: which underlying concepts improve this repository when implemented natively against its current workflow. This revision answers that question without claiming any host capability or authorizing runtime work.

Keep Beads as task and dependency authority, Git as source authority, and independent review as the acceptance boundary. The dated [baseline evidence](workflow-comparison-baseline-evidence.md) shows that the current workflow already has requirement mapping, role-separated phases, targeted validation, failure escalation, and resumable notes. The opportunity is incremental hardening of those mechanisms, not replacing them or importing Forge, Factory, Teamsters, Test Automation, or Ponytail.

Evidence grades use the [decision rubric](workflow-comparison-decision-rubric.md#evidence-quality-and-uncertainty): B is inspectable source or checked-in tests, C is documentation, and D is unknown or conflicting. Marketplace compatibility remains D where host loading is absent. That does not reduce a concept's native-design value when the proposed boundary uses current files and tools instead of marketplace code.

## Marketplace implementation portability remains separate

Do not import the marketplace as an OpenCode workflow. Forge and Factory source can inform the two native designs above, but their code, stores, schemas, and CLI contracts remain separate adaptation candidates with unproven OpenCode loading. Teamsters dispatch, Test Automation's Claude resume command, Ponytail hooks, Open Wrapper, local-provider configuration, and substantial replacement remain rejected for import for the reasons in the [risk register](workflow-comparison-opportunity-risk-register.md#opportunity-and-risk-register) and [capability assessment](local-marketplace-documentation-capability-assessment.md#decision-relevant-limits-and-unknowns).

The strongest rejected alternative is still a full replacement. It would displace planning, implementation, validation, review, recovery, and task-state interfaces while the documentary record supplies no reconciliation, migration, rollback, or host trace. The native recommendations above deliberately avoid that displacement.

## Traceability, fairness, priority, and conflict review

**Traceability.** Every recommendation above directly links to current instruction or inspected implementation evidence and marks it C, B, or D. The native rows compare those sources to the current workflow rather than treating a missing marketplace adapter as a reason to reject the concept. The capability assessment records unavailable upstream/release verification and no installation, configuration, import, trial, or live-service interaction. Those limits still apply to marketplace portability claims.

**Fairness.** The baseline is retained as a first-class option. No alternative receives credit for a feature outside its declared boundary, and no source presence, README, manifest, or checked-in test is treated as a host-load result. This follows the rubric's common-condition and gate rules.

**Priority.** The order is safety and authoritative state, then correct and independently reviewed completion, then optional maintainability improvements. Evidence freshness leads because it hardens existing requirement and acceptance evidence without changing task authority. Admission/recovery follows because it adds a bounded checkpoint but more process. Delegation is last because its native runtime seam is unverified. This applies the [decision rubric's gates and decision rules](workflow-comparison-decision-rubric.md#gates), which make safety and OpenCode feasibility non-tradeable when a candidate requires that surface and prevent time, cost, or feature breadth from compensating for a gap.

**Conflicts and missing evidence.** The material identifies potential disagreement among Beads, Forge, Factory, `.lore/work/notes`, and Claude-specific state. The native boundaries avoid that conflict by retaining Beads and Git authority and placing receipt/checkpoint information in existing work artifacts. Unsupported marketplace dispatch/hooks, no verified upstream provenance or current maintenance, no OpenCode load trace, no migration or rollback design, and no runtime effectiveness evidence continue to bar implementation import and replacement.
