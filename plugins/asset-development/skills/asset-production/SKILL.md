# Asset production

Read [asset-workflow](../asset-workflow/SKILL.md) and approval history first. Inspect the authoring source and create separate reproducible derivatives within the requested delivery scope. Requested exports, conversions and validation need no separate stage permission and may be candidates before source acceptance. Choose routine missing paths and views; ask about consequential unresolved decisions. A bounded pilot may include disposable validation. Runtime integration must be explicitly requested, including at the outset; after source acceptance continue already-requested integration without another permission turn.

## Preserve, inventory and choose derivatives

- Keep the editable authoring source immutable, along with any generator if one exists. Load detailed source and operate on a derived copy for reduction, UVs or baking. The authoring source need not have a full scene generator unless the task/consumer requires one. The derivative process itself must have a reproducible conversion recipe from its packaged inputs, including versions/settings, verified to the extent claimed. A separate production script may automate; do not simplify architecture/characters by rerunning a lower-detail source-generator variant. Write derivatives to a separate in-scope destination; never replace source or silently substitute another asset.
- Record source identity/revision, provenance, tool versions, consumer/library version, reproducible steps, assumptions and status. Pin versions when executing; inspect installed exporter options rather than guessing.
- Define portable assembly contract: axes/units (including unknowns), local origins, scene/per-instance matrices, material roles/emissive intent and study camera. Apply each transform once; do not recenter, reconstruct placement by eye or repeat loader/export axis conversion. Preserve role mapping and instance matrices when batching.
- Inventory objects, UVs/textures/channel meaning, skins/joints/animation relevant to consumer; record actual screen sizes, repetition/population and unknown device/performance targets. Previously known consumer constraints may inform feasibility, but must not silently compromise the approved visual target; resolve tradeoffs explicitly. Ask only blocking decisions; mark others unknown.
- Judge detail at intended screen size and preserve landmarks/silhouette/modular joins. Reduction, normal/AO/base/emissive textures, LOD and compression are optional only when measured screen-space or delivery benefit justifies them. Do not invent budgets. Normal maps add shading, not silhouette; AO may double-darken/stale; avoid baking fixed lighting into shared base maps. Keep shared appearance useful across intended modes; reserve emissive maps for self-lit accents.

## Consumer validation and handoff

- glTF does not carry arbitrary Blender node graphs or automatically reproduce custom shading. Verify actual consumer loader's handling of materials, textures, transforms, skins and animation. Successful GLB transfer is distinct from accepted appearance in the actual browser/runtime consumer. For appearance, compare paired relevant modes using same geometry, camera and role mapping; compare scene pixels, not only background. Renderer lighting differences mean matching numeric values is not matching appearance. Document deliberate material-treatment tradeoffs, not as exporter defects. Blender beauty render alone is not runtime proof.
- Use a representative pilot only for a new/unproven export/consumer path; reuse proven patterns without redundant pilots. Change one optional production choice at a time; compare unchanged source in intended view, document change/reason/measured evidence, inspect exported artifact and actual loader warnings/unsupported behavior.
- Report counts with meaning: unique resources vs placed totals; multiply geometry per instance by instance count for assembled totals. Linked/reused meshes or clones are not GPU instancing. Preserve matrices/material assignments when batching. Distinguish assembled totals, frame-visible triangles, draw calls and decoded storage. These are not GPU-memory/target budgets; state method and limits. Small regression fixture should cover ordinary mesh and instanced mesh count >1.
- Deliver a lean derivative package: current derivative, reproducible conversion recipe, concise report and selected evidence. Consolidate useful artifacts and reproduction steps; keep scratch candidates out of commits by default. At acceptance, cleanup requires explicit authorization: present a keep/delete inventory, check links and dependencies, and independently open/validate the consolidated package before removing specifically authorized duplicates or superseded files. Never delete the only approved source/evidence or assume experiment-path assets are disposable. State open decisions and consumer caveats. Measure requested performance optimization on a derivative without changing the source; ask about material visual compromises. Do not invent budgets or imply that a native-scene check proves runtime readiness.
- Preserve exact concept approval before modeling and final candidate visual acceptance; checks are not approval. Inspect requested derivatives for fidelity and label unaccepted outputs candidates, without adding a mandatory intermediate review turn. Verify requested integration in the actual consumer and present runtime appearance for acceptance. Route consequential visual/design decisions to the user/designer. Mechanical packaging is not authority to redesign geometry/material direction. Never silently substitute a specialist or broaden scope.

Project-specific pipeline references should be taken from the consuming project's authorized context/guide; this skill contains generic validation principles only.
