# Asset workflow

The user is the visual director; the agent owns the brief, execution, evidence, and handoff. These instructions describe how to execute work and do not themselves authorize concept generation, modeling, production derivatives, integration, or asset creation. Obtain task authorization and preserve every approval boundary. Do not install software or dependencies; report the blocker and request direction if they are needed. Runtime integration remains a separate, explicitly authorized step below.

## Context and approvals

Consult `<project-root>/docs/asset-direction.md` when present; it may link to a project-specific guide. Direction is not approval for an individual asset. If absent, rely on the user brief and authorized references. Ask only for missing decisions that block the next authorized step; do not require a context file.

Never collapse or infer these gates:

1. **Description approval:** write a concise brief; obtain explicit approval of purpose, silhouette, style, readability, intended consumer, and constraints. A general request is not approval of a proposed description.
2. **Choose a branch:** exploratory imagery uses [concept-art](../concept-art/SKILL.md), requiring exact-version concept approval before Blender modeling. Production 2D art uses [asset-art](../asset-art/SKILL.md), requiring separately authorized generation and exact-version artwork approval. A concept is not production art; a brief and this skill authorize neither.
3. **Model and critique:** use [blender-model](../blender-model/SKILL.md) and [blender-visualize](../blender-visualize/SKILL.md) to inspect actual saved geometry. For complex scenes, establish complete composition and scope coverage with a composition map or equivalent, then review the whole-scene blockout before detailing. Decompose into connected assemblies with explicit ownership, interfaces, and reference authority; component studies clarify the whole, not replace it. A concept guides design, not pixel matching unless requested. Iterate in bounded batches from the latest accepted aggregate, preserving approved areas while allowing specifically authorized, localized interface changes. Assess silhouette, proportion, construction, detail, topology, and visible defects in actual neutral/restrained renders. For complex or consequential work, include an independent visual critique when available and authorized; treat it as evidence, not an automatic gate. Consolidate material findings by view and severity; structural checks and critique inform but do not replace user visual judgment. Stop when the authorized target is accepted or remaining changes lack material benefit; present caveats for user judgment rather than pursuing endless perfection. Presentation differences alone need not trigger geometry changes; final appearance is a separate assessment. Obtain explicit model approval; concept approval is not model approval.
4. **Integration and acceptance:** only after the relevant approved source, integrate into the actual runtime under separate authorization. Verify in the actual consumer and obtain separate explicit runtime acceptance. Screenshots or successful checks do not imply acceptance.

After model acceptance, use [asset-production](../asset-production/SKILL.md) for explicitly authorized production derivatives and their review before promotion. Production authorization is not integration authorization. The 2D branch similarly keeps artwork, derivatives, integration, and acceptance separate.

Pilot approval plus explicit authorization for a defined remainder permits parallel independent work where practical and one combined end review; do not interrupt for redundant approvals inside that scope. Pause for new scope, material/design decisions, or blockers. If approval is withheld, return to the relevant gate and reset approvals proportionally. Preserve approved versions and decision history. Silence, renders, broad requests, and checks are not approval.

## Routing and maintained handoff

Visual direction belongs to the user/designer. Use only available specialists and tools authorized for the task; unavailable route/model is a blocker to report, not permission to silently substitute another visual specialist. Keep the maintained package stable and relocatable. The approved editable native source (for Blender, the `.blend`) is the default primary model deliverable; a full deterministic generator is required only when the task or consumer specifically requires one. Preserve source identity/provenance, useful checkpoints and operation history, reopen validation, genuinely reusable preview/validation tools, approved brief/concepts, selected final evidence, and a concise README. Distinguish reusable tools and process records from one-off scripts, logs, and scratch. Record permissions, approval states/revision history, tool versions, reproduction steps where applicable, orientation/scale, measured bounds, expected consumer, and limitations. Mark pending outputs candidates. Stable filenames are preferred; permanent numbered iteration directories are not required.

Never overwrite the approved/current source during active iteration: work on a separate candidate and preserve the prior version until the candidate is reopened, checked, rendered, and reviewed. Do not silently reduce approved scope; track every required family, including secondary elements, and record omissions only when the user authorizes them. Protection is a guardrail, not a reason to ignore a visible interface conflict: request or use only explicit, localized authority to change protected neighboring work, and record the change and caveat. Keep production exports separate from authoring sources; create only within authorized derivative/export work and integrate only under separate authorization.

At acceptance, consolidate only with explicit cleanup authorization. Keep the approved editable master and required dependencies, approved concepts, a small set of final renders, a concise README, useful reusable tools, and selected process/approval evidence. First present a keep/delete inventory; check dependencies and document links, then independently reopen and render the consolidated package. Only after verification and explicit authorization may identified duplicates, superseded copies, one-off scripts, or logs be removed. Never assume an experiment path makes accepted work disposable, and never delete the only approved source/evidence or otherwise discard work without authorization. Keep scratch bounded during work. Keep native image staging until durable copy and provenance are verified.

Choose Git, LFS, or external storage according to project policy; explain size and backup consequences. Do not categorically exclude binaries, install LFS, or commit without authorization. Claim reproducibility only for a regeneration or conversion process actually verified from packaged inputs. Known consumer/runtime constraints may inform feasibility, but do not silently compromise the approved visual target; resolve tradeoffs explicitly. Do not invent polygon, texture, draw-call, memory, or performance budgets; mark unknowns unknown. Assess performance only in a separately authorized, measured derivative/consumer task after source visual/model acceptance. Preserve separate description, concept/artwork, model, derivative, integration, and runtime-acceptance decisions.
