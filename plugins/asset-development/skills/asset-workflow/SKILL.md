# Asset workflow

The user is the visual director; the agent owns the brief, execution, inspection, refinement, evidence, and handoff. Pause for visual judgment, not routine execution. The user's request authorizes work within its stated scope; loading a skill alone does not authorize asset creation. Do not install software or dependencies; report the blocker and request direction if they are needed. Runtime integration requires explicit scope, which may already be supplied in the original request.

## Direction, visual checkpoints, and execution

Consult `<project-root>/docs/asset-direction.md` when present; it may link to a project-specific guide. Direction is not approval for an individual asset. If absent, rely on the user brief and authorized references. Ask only for missing decisions that block the next authorized step; do not require a context file.

Separate authorization to do work from approval of its visual result. A request to build an asset authorizes the production work, subject to the concept checkpoint below; it does not mean the user has accepted an unseen result. Record the relevant decisions without requiring a separate conversational turn for each.

1. **Establish the brief:** capture purpose, silhouette, style, readability, intended consumer, and constraints from the request and authorized references. Ask only about consequential missing visual decisions; do not require a standalone description-approval turn when the request provides enough direction. If image generation is requested, proceed to concepts without asking the user to authorize that same generation again. A modeling-only request does not itself authorize image generation; ask once if concept generation is needed.
2. **Review the concept before modeling:** use [concept-art](../concept-art/SKILL.md) to present actual verified concept imagery. Obtain the user's approval of the selected exact version before building the model. For an existing model or approved concept, use the established visual direction; do not restart concept exploration for routine in-scope revisions. If the user requested the model, concept approval releases that already-authorized work without another "may I model it?" turn. A concept-only request ends at concept delivery unless the user extends scope. Production 2D work uses [asset-art](../asset-art/SKILL.md) instead; its final artwork is reviewed as the deliverable, not automatically preceded by a separate concept or brief approval.
3. **Build, inspect, and refine autonomously:** use [blender-model](../blender-model/SKILL.md) and [blender-visualize](../blender-visualize/SKILL.md) to build and inspect actual saved geometry against the approved direction. For complex scenes, map complete composition, connected assemblies, interfaces, and scope coverage; inspect the whole-scene blockout before detailing. These are agent-owned checks, not mandatory user gates. Component studies clarify the whole, not replace it. A concept guides design, not pixel matching unless requested. Iterate in bounded batches from the latest accepted aggregate, preserving approved areas. Assess silhouette, proportion, construction, detail, topology, and visible defects in actual neutral/restrained renders. Include independent visual critique for complex or consequential work when available within scope; treat it as evidence, not an automatic gate. Consolidate material findings by view and severity. Do not ask permission for routine diagnostic views, checks, or corrections within the approved direction. Pause if a consequential visual choice cannot be resolved from that direction, scope changes, or a real permission boundary blocks progress. Stop when the candidate meets the target or further refinement lacks material benefit; present caveats rather than pursuing endless perfection.
4. **Present the finished candidate:** show the actual inspected model or production artwork for user judgment. Technical checks and agent critique do not imply visual acceptance. Preserve the distinction between approved concept and accepted final asset without inserting approval turns for intermediate operations.

Use [asset-production](../asset-production/SKILL.md) for requested derivatives, including preview or delivery exports needed to assess the candidate. Exporting, converting, and validating requested formats are part of that delivery scope, not new permission gates. Preserve the editable source and label unaccepted outputs candidates; inspect derivatives for visual fidelity before handoff. Do not silently redesign or optimize away approved features.

Runtime integration must be explicitly requested, but that authorization may cover the full task from the outset. After source acceptance, continue into already-requested integration without another permission turn. Verify in the actual consumer and present runtime appearance for acceptance; screenshots or successful checks are evidence, not acceptance. Deployment or edits outside the authorized project remain subject to their own permissions.

Pilot approval plus a request for a defined remainder permits parallel independent work where practical and one combined end review. Apply the same continuity within every authorized stage. One user message can approve a candidate and authorize the next scope; record both without asking twice. If approval is withheld, revise within the requested direction or clarify the material change, retaining unaffected approvals. Silence and checks are not approval, but an explicit request is authorization to execute its scope.

## Routing and maintained handoff

Visual direction belongs to the user/designer. Use only available specialists and tools authorized for the task; unavailable route/model is a blocker to report, not permission to silently substitute another visual specialist. Keep the maintained package stable and relocatable. The approved editable native source (for Blender, the `.blend`) is the default primary model deliverable; a full deterministic generator is required only when the task or consumer specifically requires one. Preserve source identity/provenance, useful checkpoints and operation history, reopen validation, genuinely reusable preview/validation tools, approved brief/concepts, selected final evidence, and a concise README. Distinguish reusable tools and process records from one-off scripts, logs, and scratch. Record permissions, approval states/revision history, tool versions, reproduction steps where applicable, orientation/scale, measured bounds, expected consumer, and limitations. Mark pending outputs candidates. Stable filenames are preferred; permanent numbered iteration directories are not required.

Never overwrite the approved/current source during active iteration: work on a separate candidate and preserve the prior version until the candidate is reopened, checked, rendered, and reviewed. Do not silently reduce approved scope; track every required family, including secondary elements, and record omissions only when the user authorizes them. Protection is a guardrail, not a reason to ignore a visible interface conflict: request or use only explicit, localized authority to change protected neighboring work, and record the change and caveat. Keep production exports separate from authoring sources; requested exports need no additional authorization, while unrequested derivatives or integration do not become authorized merely because a source is accepted.

At acceptance, consolidate only with explicit cleanup authorization. Keep the approved editable master and required dependencies, approved concepts, a small set of final renders, a concise README, useful reusable tools, and selected process/approval evidence. First present a keep/delete inventory; check dependencies and document links, then independently reopen and render the consolidated package. Only after verification and explicit authorization may identified duplicates, superseded copies, one-off scripts, or logs be removed. Never assume an experiment path makes accepted work disposable, and never delete the only approved source/evidence or otherwise discard work without authorization. Keep scratch bounded during work. Keep native image staging until durable copy and provenance are verified.

Choose Git, LFS, or external storage according to project policy; explain size and backup consequences. Do not categorically exclude binaries, install LFS, or commit without authorization. Claim reproducibility only for a regeneration or conversion process actually verified from packaged inputs. Known consumer/runtime constraints may inform feasibility, but do not silently compromise the approved visual target; resolve tradeoffs explicitly. Do not invent polygon, texture, draw-call, memory, or performance budgets; mark unknowns unknown. Measure performance within requested derivative/consumer work; material visual compromises require user judgment. Record task authorization, approved concept, final visual acceptance, and runtime acceptance where applicable without turning routine production steps into permission gates.

When revising these instructions, use [evals/cases.md](evals/cases.md) to check execution continuity, visual judgment, and retained safety boundaries.
