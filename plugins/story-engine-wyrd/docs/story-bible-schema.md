# Story Bible Schema Documentation

This document defines the complete schema for the `.story-state/` directory structure and all story bible files used by the multi-agent `/write-story` command. These schemas serve as the contract for all agent outputs and orchestrator file operations.

## Directory Structure

### Flat Chapter Organization

For stories without explicit part structure:

```
.story-state/
└── [Story-Title]/
    ├── PLAN.md                          # Master plan with story concept and chapter summaries
    ├── metadata.json                    # Progress tracking and state management
    ├── quality-rubrics.md               # Validation criteria for quality checks
    ├── final-review-notes.md            # Final read-through agent's progressive notes
    ├── characters/
    │   ├── protagonist-[name].md        # Main character profile
    │   ├── antagonist-[name].md         # Primary antagonist profile
    │   └── supporting-[name].md         # Supporting character profiles
    ├── world-state/
    │   ├── mechanics.md                 # Established world rules (magic/tech systems)
    │   ├── locations.md                 # Places visited in the story
    │   └── timeline.md                  # Chronological event tracking
    ├── plot-threads/
    │   ├── thread-[name].md             # Individual plot thread tracking
    │   └── thread-status.md             # Active/resolved thread summary
    └── chapters/
        ├── chapter-01.md                # Generated prose for chapter 1
        ├── chapter-02.md                # Generated prose for chapter 2
        └── ...
```

### Part-Based Chapter Organization

For stories with explicit part structure (e.g., 3-act structure, multi-book series):

```
.story-state/
└── [Story-Title]/
    ├── PLAN.md
    ├── metadata.json
    ├── quality-rubrics.md
    ├── final-review-notes.md
    ├── characters/
    │   └── ...
    ├── world-state/
    │   └── ...
    ├── plot-threads/
    │   └── ...
    └── chapters/
        ├── part-1/
        │   ├── chapter-01.md
        │   ├── chapter-02.md
        │   └── ...
        ├── part-2/
        │   ├── chapter-01.md
        │   ├── chapter-02.md
        │   └── ...
        └── part-3/
            └── ...
```

**Naming Conventions**:
- Directory names use kebab-case derived from story title (e.g., "Cyberpunk Rebellion" → `Cyberpunk-Rebellion/`)
- Character files use role prefix: `protagonist-`, `antagonist-`, `supporting-`
- Chapter files use zero-padded numbers: `chapter-01.md`, `chapter-02.md`, etc.
- Plot thread files use descriptive names: `thread-redemption-arc.md`, `thread-conspiracy-reveal.md`

## File Schemas

### PLAN.md Schema

The master plan file containing story concept, narrative structure, and chapter-by-chapter summaries.

#### Frontmatter

```yaml
---
title: "Story Title"                     # REQUIRED: Full story title
world: "Telvaren"                        # REQUIRED: World name (or "Original" for non-established worlds)
lens: "Mystery"                          # OPTIONAL: Genre lens transformation (or null/None)
format: "Epic"                           # REQUIRED: Story format (Flash Fiction, Short Story, Epic, Serialized)
created: "2025-11-16"                    # REQUIRED: ISO date (YYYY-MM-DD) of creation
total_chapters: 30                       # REQUIRED: Total number of chapters planned
part_structure: "3-act"                  # OPTIONAL: Part organization ("3-act", "4-part", "trilogy", etc.)
version: "1.0.0"                         # REQUIRED: Semantic version of this plan
---
```

**Field Specifications**:
- `title`: String, no character limit, used to derive directory name
- `world`: String, must match existing world definition or "Original"
- `lens`: String or null, must match existing lens definition if provided
- `format`: Enum: `"Flash Fiction"`, `"Short Story"`, `"Epic"`, `"Serialized"`
- `created`: String in ISO 8601 format (YYYY-MM-DD)
- `total_chapters`: Integer, minimum 1, no upper limit
- `part_structure`: String or null, free-form description of part organization
- `version`: String in semantic versioning format (MAJOR.MINOR.PATCH)

#### Markdown Body

```markdown
# [Story Title] - Master Plan

## Story Concept

[Comprehensive narrative overview generated by concept-developer agent, including:]
- Central conflict and stakes
- Protagonist's external desire and internal need
- Antagonist's motivation and obstacles
- World mechanics and key locations
- Thematic focus
- Narrative arc structure (setup, escalation, climax, resolution)
- Tone and atmosphere

## Character Summary

Brief overview of main characters:
- **Protagonist**: [Name] - [One-sentence description]
- **Antagonist**: [Name] - [One-sentence description]
- **Supporting**: [Names] - [Roles in narrative]

## Chapter Summaries

### Chapter 1: [Chapter Title]

- **Purpose**: [Role in overall narrative arc - setup, escalation, climax, etc.]
- **Events**: [Key plot beats and actions that occur]
- **Character Arcs**: [Character development moments and decisions]
- **Plot Threads**: [Which threads are introduced, advanced, or resolved]
- **Word Count Target**: [e.g., 3000-4000]

### Chapter 2: [Chapter Title]

[Same structure as Chapter 1]

[...repeat for all chapters]
```

**Section Requirements**:
- **Story Concept**: 500-2000 words, comprehensive enough for agents to understand narrative direction
- **Character Summary**: Brief list, full details in character files
- **Chapter Summaries**: ONE section per chapter, numbered sequentially, all 5 fields required per chapter

### Character File Schema

Individual character profile files stored in `characters/` directory.

#### Frontmatter

```yaml
---
name: "Character Name"                   # REQUIRED: Character's canonical name
role: "protagonist"                      # REQUIRED: "protagonist", "antagonist", or "supporting"
created: "2025-11-16"                    # REQUIRED: ISO date of creation
last_updated: "2025-11-16"               # REQUIRED: ISO date of last modification
---
```

**Field Specifications**:
- `name`: String, character's full name as it appears in narrative
- `role`: Enum: `"protagonist"`, `"antagonist"`, `"supporting"`
- `created`: String in ISO 8601 format (YYYY-MM-DD)
- `last_updated`: String in ISO 8601 format (YYYY-MM-DD)

#### Markdown Body

```markdown
# Character Profile: [Name]

## Core Traits

- **External Desire**: [Plot-level goal - what the character wants to achieve]
- **Internal Need**: [Character growth requirement - what the character needs to learn/become]
- **Fear**: [Core fear that creates hesitation and internal conflict]
- **Distinctive Voice**: [Speech patterns, vocabulary, mannerisms, verbal tics]

## Physical Description

[Detailed appearance for consistency across chapters:]
- Age, height, build
- Hair color, eye color, distinctive features
- Clothing style, accessories
- Physical mannerisms (posture, gestures, expressions)

[Include enough detail for continuity validation to detect contradictions]

## Character Arc

- **Start**: [Initial state at beginning of story - beliefs, capabilities, relationships]
- **Pressure**: [Forces that drive change - events, relationships, revelations]
- **Choice**: [Key decision point(s) where character must choose between desire and need]
- **End**: [Transformation by story's end - how character has changed or failed to change]

## Relationships

- **[Character Name 1]**: [Nature of relationship, dynamics, history, conflicts]
- **[Character Name 2]**: [Nature of relationship, dynamics, history, conflicts]

[List all significant relationships with other characters]

## Scenes Featuring This Character

- **Chapter 1**: [Role in scene, key actions, character moments]
- **Chapter 5**: [Role in scene, key actions, character moments]
- **Chapter 12**: [Role in scene, key actions, character moments]

[Updated by agents as character appears in new chapters]
```

**Section Requirements**:
- **Core Traits**: All 4 fields required (External Desire, Internal Need, Fear, Distinctive Voice)
- **Physical Description**: Minimum 100 words, must include hair color, eye color, age
- **Character Arc**: All 4 fields required (Start, Pressure, Choice, End)
- **Relationships**: At least 1 relationship for protagonist/antagonist, optional for supporting
- **Scenes Featuring This Character**: Updated incrementally as chapters are generated

### metadata.json Schema

Progress tracking and state management file.

```json
{
  "story_title": "Cyberpunk Rebellion",
  "format": "Epic",
  "total_chapters": 30,
  "completed_chapters": 15,
  "current_status": "in_progress",
  "current_phase": "prose-approved",
  "selection_pending": false,
  "last_session": "2025-11-16",
  "continuity_checkpoints": [3, 6, 9, 12, 15],
  "quality_issues_found": 2,
  "quality_issues_resolved": 2,
  "incomplete_chapters": [],
  "part_structure": "3-act"
}
```

**Field Specifications**:
- `story_title`: String, matches `title` from PLAN.md frontmatter
- `format`: String, matches `format` from PLAN.md frontmatter
- `total_chapters`: Integer, matches `total_chapters` from PLAN.md frontmatter
- `completed_chapters`: Integer, count of fully generated and quality-checked chapters
- `current_status`: Enum: `"in_progress"`, `"complete"`, `"paused"`, `"error"`
- `current_phase`: Enum: Phase state tracking for Verbalized Sampling (VS) workflow. Supports the following states:
  - `"concept-sampling"`: Concept generation in progress, sample file exists, awaiting user selection
  - `"concept-approved"`: Concept selected, approved concept file created, ready for character building
  - `"character-sampling"`: Character generation in progress for one or more characters, sample files exist
  - `"character-approved"`: All characters selected and approved, ready for prose generation
  - `"prose-sampling"`: Chapter generation in progress, sample file exists, awaiting auto-selection or user selection
  - `"prose-approved"`: Chapter selected and approved, ready for next chapter or completion
- `selection_pending`: Boolean, true if user cancelled selection during user-choice phases (concept/character), preserves sample file and allows workflow resume from selection step (per REQ-F-27)
- `last_session`: String in ISO 8601 format (YYYY-MM-DD), date of last generation session
- `continuity_checkpoints`: Array of integers, chapter numbers where continuity validation ran
- `quality_issues_found`: Integer, cumulative count of issues flagged by quality-checker
- `quality_issues_resolved`: Integer, cumulative count of issues resolved
- `incomplete_chapters`: Array of integers, chapter numbers with partial/failed generation
- `part_structure`: String or null, matches `part_structure` from PLAN.md frontmatter

**Update Triggers**:
- `completed_chapters`: Incremented after each successful chapter generation + quality check
- `current_status`: Set to "complete" when `completed_chapters == total_chapters`
- `current_phase`: Updated after each VS workflow step:
  - Set to `"concept-sampling"` when concept-developer begins generating samples
  - Set to `"concept-approved"` when user selects concept and concept-approved.md is created
  - Set to `"character-sampling"` when character-builder begins generating samples for a character
  - Set to `"character-approved"` when all character selections are complete
  - Set to `"prose-sampling"` when prose-writer begins generating chapter samples
  - Set to `"prose-approved"` when chapter selection (auto or manual) is complete
- `selection_pending`: Set to `true` when user cancels selection during user-choice phases (concept/character), set to `false` when selection completes
- `last_session`: Updated at start of each `/write-story` or resume session
- `continuity_checkpoints`: Appended after each continuity validation run
- `quality_issues_found`: Incremented when quality-checker flags issues
- `quality_issues_resolved`: Incremented when issues are fixed (regeneration or user approval)
- `incomplete_chapters`: Chapters added when generation produces empty/error output

**VS Workflow State Transitions**:

The `current_phase` field tracks progress through the Verbalized Sampling (VS) workflow. VS is a prompting technique that generates k=5 candidate outputs at key decision points, allowing users to select from creative variations instead of accepting a single "most typical" output.

Phase states use `-sampling` and `-approved` suffixes to distinguish between generation and selection steps:

```
Story Creation Flow:
┌─────────────────────┐
│  concept-sampling   │  ← concept-developer generates 5 concept variations
└──────────┬──────────┘
           │ (user selects one)
           ▼
┌─────────────────────┐
│  concept-approved   │  ← selected concept written to concept-approved.md
└──────────┬──────────┘
           │ (PLAN.md generated from approved concept)
           ▼
┌─────────────────────┐
│ character-sampling  │  ← character-builder generates 5 variations per character
└──────────┬──────────┘
           │ (user selects each character)
           ▼
┌─────────────────────┐
│ character-approved  │  ← all characters selected, written to character files
└──────────┬──────────┘
           │ (prose generation begins)
           ▼
┌─────────────────────┐
│   prose-sampling    │  ← prose-writer generates 5 chapter variations
└──────────┬──────────┘
           │ (auto-select highest probability, or user override)
           ▼
┌─────────────────────┐
│   prose-approved    │  ← chapter written, ready for next chapter
└─────────────────────┘
           │ (repeat prose cycle for each chapter)
           ▼
        (complete)
```

**Resume from Interrupted Sampling**:

The `-sampling` and `-approved` states enable workflow resume from interrupted VS phases:

1. If `current_phase` is `"concept-sampling"` and `concept-samples.md` exists but `concept-approved.md` does not, resume workflow spawns sampling-curator to complete selection
2. If `current_phase` is `"character-sampling"` and `character-samples-[name].md` exists, resume workflow spawns sampling-curator for that character
3. If `current_phase` is `"prose-sampling"` and `chapter-[NN]-samples.md` exists, resume workflow spawns sampling-curator for that chapter
4. If `selection_pending` is `true`, user cancelled during selection - sample file is preserved for manual selection on resume

This state tracking prevents re-running generation when only selection is needed, improving resume efficiency and preserving user progress.

### quality-rubrics.md Schema

Validation criteria used by quality-checker agent for per-chapter validation.

```markdown
# Quality Rubrics for [Story Title]

## World Consistency

- [ ] No violations of established world mechanics (magic/technology rules)
- [ ] Technology/magic use follows defined capabilities and limitations
- [ ] Geography and locations match previous descriptions
- [ ] Timeline and chronology are accurate (no time contradictions)
- [ ] Cultural norms and social structures remain consistent

## Character Voice

- [ ] Speech patterns consistent with character profile (vocabulary, syntax, verbal tics)
- [ ] Decisions align with established motivations and internal conflicts
- [ ] Character reactions fit personality and emotional state
- [ ] Character knowledge reflects what they've experienced (no unexplained insights)
- [ ] Physical descriptions match character files (eye color, height, etc.)

## Prose Clarity

- [ ] No unclear antecedents or ambiguous pronoun references
- [ ] Scene transitions are clear (time, location, POV shifts marked)
- [ ] Action sequences are followable (cause and effect explicit)
- [ ] Pacing appropriate for scene type (action fast, introspection slower)
- [ ] No confusing sentence structures or grammatical errors

## Dialogue Authenticity

- [ ] Characters sound distinct from each other (unique voices)
- [ ] Dialogue serves plot advancement or character development (no filler)
- [ ] Subtext present in important conversations (characters don't state everything)
- [ ] Dialogue tags vary appropriately (not all "said")
- [ ] Balance of dialogue and narrative description

## Plot Logic

- [ ] Events follow causally from previous chapters (no unexplained occurrences)
- [ ] No unresolved contradictions with prior plot points
- [ ] Stakes escalate appropriately for story position (rising tension)
- [ ] Character goals and obstacles are clear
- [ ] Chapter advances plot threads identified in PLAN.md

## Thematic Alignment

- [ ] Chapter serves story's central themes (from PLAN.md Story Concept)
- [ ] Motifs are reinforced (recurring symbols, images, phrases)
- [ ] Tone matches established atmosphere (horror stays tense, romance stays hopeful, etc.)
- [ ] Character arcs advance thematic questions
- [ ] Scene choices support thematic resonance
```

**Structure Requirements**:
- **6 rubric categories**: World Consistency, Character Voice, Prose Clarity, Dialogue Authenticity, Plot Logic, Thematic Alignment
- **5 checklist items per category**: Each item is a specific, measurable criterion
- **Checkbox format**: Use `- [ ]` for quality-checker agent to mark during validation
- **Story-specific**: Generated per story based on PLAN.md (e.g., mystery stories add "clue placement" checks)

**Usage**:
- Quality-checker agent reads this file before validating each chapter
- Agent marks checkboxes and provides detailed feedback for failed criteria
- Rubrics can be customized by user (edit file to add story-specific checks)

## Verbalized Sampling Files

The Verbalized Sampling (VS) system generates temporary sample files containing k=5 candidate outputs at specific generation phases. These files follow a consistent schema across all VS-enabled agents (concept-developer, character-builder, prose-writer).

### concept-samples.md Schema

Temporary file containing 5 concept variations for user selection.

#### Frontmatter

```yaml
---
title: "[Story Title]"                       # REQUIRED: Story title
phase: concept-sampling                      # REQUIRED: Fixed value "concept-sampling"
story_directory: .story-state/[Story-Title]/ # REQUIRED: Path to story state directory
created: YYYY-MM-DD                          # REQUIRED: ISO date of generation
k: 5                                         # REQUIRED: Fixed value 5 (number of samples)
---
```

**Field Specifications**:
- `title`: String, proposed story title
- `phase`: Enum: `"concept-sampling"` (fixed value indicating VS phase)
- `story_directory`: String, path to story state directory
- `created`: String in ISO 8601 format (YYYY-MM-DD)
- `k`: Integer, fixed at 5 for all VS phases

#### Markdown Body

```markdown
# Concept Samples

## Sample 1: [Approach Name]
**Probability: 0.XX**
**Differentiator:** [One sentence on unique direction]
**Diversity Dimensions:** [narrative-voice, structural-approach, emotional-arc, thematic-focus - list 2+]

### Story Concept
[Full concept content matching PLAN.md Story Concept section format]

### Character Summary
[Characters as would appear in PLAN.md]

### Chapter Summary Preview
[First 3-5 chapters to show structural approach]

---
## Sample 2: [Approach Name]
**Probability: 0.XX**
**Differentiator:** [One sentence on unique direction]
**Diversity Dimensions:** [narrative-voice, structural-approach, emotional-arc, thematic-focus - list 2+]

### Story Concept
[Full concept content]

### Character Summary
[Characters]

### Chapter Summary Preview
[Preview chapters]

---
## Sample 3: [Approach Name]
[Same structure as Sample 1-2]

---
## Sample 4: [Approach Name]
[Same structure as Sample 1-2]

---
## Sample 5: [Approach Name]
[Same structure as Sample 1-2]
```

**Sample Structure Requirements**:
- **Approach Name**: String, descriptive label for the creative approach (e.g., "Dark Revenge Tale", "Redemption Journey", "Mystery Unraveling")
- **Probability**: Float in 0.XX format (e.g., 0.23, 0.18), must sum to approximately 1.0 across all 5 samples (acceptable range: 0.95-1.05)
- **Differentiator**: String, one-sentence explanation of what makes this concept unique compared to other samples
- **Diversity Dimensions**: Array of strings, lists which creative dimensions vary in this sample. Valid dimensions for concept phase:
  - `narrative-voice`: First person vs third person, intimate vs distant, reliable vs unreliable narrator
  - `structural-approach`: Linear vs non-linear, single POV vs multiple, chapter structure style
  - `emotional-arc`: Tragedy vs triumph, steady vs rollercoaster, hopeful vs dark
  - `thematic-focus`: Primary theme emphasis (justice, identity, power, love, survival, etc.)
  - Must list at least 2 dimensions per sample to demonstrate creative diversity

**Content Sections**:
- **Story Concept**: Full narrative overview matching PLAN.md format (500-2000 words)
- **Character Summary**: Brief character list as would appear in approved PLAN.md
- **Chapter Summary Preview**: First 3-5 chapter summaries to demonstrate structural approach and pacing

**Lifecycle**:
- Created by concept-developer agent with VS mode enabled
- Parsed by sampling-curator agent for user selection
- Deleted after successful selection (winning concept written to concept-approved.md)
- Preserved on user cancellation to allow workflow resume

### VS File Validation Rules

**Probability Validation**:
- All 5 samples must have probability field
- Each probability must be in 0.XX format (0.00 to 1.00)
- Sum of all 5 probabilities must be between 0.95 and 1.05 (accounts for rounding)
- If parsing fails: assign equal weights (0.20 each) and warn user

**Diversity Validation**:
- Each sample must list at least 2 diversity dimensions
- Dimensions must come from valid set for that phase (concept/character/prose)
- Dimension names must match expected values (exact string match)

**Content Completeness**:
- All required sections must be present (Story Concept, Character Summary, etc.)
- Minimum word counts apply (e.g., 100 words for Physical Description)
- No placeholder text (e.g., "[TODO]", "[Insert content here]")

**Insufficient Candidates Error Handling**:
- If fewer than 5 samples generated: retry once with explicit instruction
- If retry still produces <5: proceed with available samples and warn user
- Never block workflow on insufficient samples after retry

**Cleanup Verification**:
- After selection, sample files must be deleted
- If cleanup fails: log warning but do not block workflow
- User cancellation preserves sample files for resume

## Validation Rules

### Frontmatter Validation

**Required Fields**:
- All schemas specify which frontmatter fields are REQUIRED
- Missing required fields should be flagged as errors on file read
- Validation should report specific missing field names

**Data Type Validation**:
- String fields: any text
- Integer fields: whole numbers only
- Boolean fields: true/false
- Date fields: YYYY-MM-DD format
- Enum fields: must match one of specified values exactly

**Example Validation Errors**:
```
ERROR: characters/protagonist-aria.md
  - Missing required field: 'role'
  - Invalid date format in 'created': '11-16-2025' (expected YYYY-MM-DD)

ERROR: PLAN.md
  - Invalid enum value in 'format': 'Novel' (expected one of: Flash Fiction, Short Story, Epic, Serialized)
  - Field 'total_chapters' must be integer, got: '30'
```

### Content Validation

**PLAN.md**:
- Must have chapter summaries matching `total_chapters` count
- Each chapter summary must have all 5 required fields (Purpose, Events, Character Arcs, Plot Threads, Word Count Target)

**Character Files**:
- Physical Description must be minimum 100 words
- All 4 Core Traits fields required
- All 4 Character Arc fields required

**Chapter Files**:
- Minimum 100 words in body
- Maximum 10,000 words (warning, not error)
- `chapter_number` must match filename (chapter-05.md must have `chapter_number: 5`)

### Cross-File Consistency Validation

**metadata.json vs PLAN.md**:
- `story_title` must match
- `format` must match
- `total_chapters` must match

**Chapter Files vs PLAN.md**:
- Each chapter number in PLAN.md should have corresponding file
- Chapter titles should match between PLAN.md and chapter frontmatter

**Character Files vs Chapters**:
- Character names in chapters should have corresponding character files
- Physical descriptions in prose should match character file descriptions

## Schema Extension Guidelines

When adding new fields to schemas:

1. **Add to Frontmatter**: New structured data goes in YAML frontmatter
2. **Add to Sections**: New narrative content goes in markdown body sections
3. **Maintain Backwards Compatibility**: Make new fields optional initially
4. **Document in This File**: Update schema documentation with new fields
5. **Update Validation**: Add validation rules for new fields
6. **Version Bump**: Increment schema version in this file's frontmatter

## Agent Output Responsibilities

### concept-developer Agent

**Outputs**:
- `PLAN.md` (complete file with frontmatter + all sections)
- `quality-rubrics.md` (customized for story's world/genre/themes)
- `world-state/mechanics.md` (initial world rules from plan)
- `plot-threads/thread-status.md` (initial thread list)
- Individual thread files for each major plot thread

### character-builder Agent

**Outputs**:
- `characters/[role]-[name].md` (one file per character)
- Updates `PLAN.md` Character Summary section with character list

### prose-writer Agent

**Outputs**:
- `chapters/chapter-[NN].md` or `chapters/part-[N]/chapter-[NN].md`
- Updates character files' "Scenes Featuring This Character" sections
- Updates `world-state/timeline.md` with new events
- Updates plot thread files with chapter progression

### quality-checker Agent

**Outputs**:
- Validation report (not persisted to file, returned to orchestrator)
- Sets `quality_checked: true` in chapter frontmatter
- Updates `metadata.json` quality issue counts

### continuity-validator Agent

**Outputs**:
- Continuity report (not persisted to file, returned to orchestrator)
- Updates `metadata.json` continuity checkpoint array
- Flags contradictions for orchestrator to resolve
